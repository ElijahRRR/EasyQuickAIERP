# EasyQuickAIERP V1 交付与验收门槛

> 版本：v0.1  
> 日期：2026-10-22  
> 状态：配套验收提案；与 [V1 范围](./01-v1-scope-and-priorities.md)一起确认。  
> 本文提供发布所需的关键验收场景，不宣称替代后续逐页面、逐接口的完整测试用例。

## 1. 什么才算交付完成

每一项 F01–F26 至少应有以下证据：

1. **可用入口**：有权限的人可以实际完成业务；要求批量的能力同时提供批量入口。
2. **业务结果**：可以查询实际对象、历史版本、结果、失败原因或待处理事项。
3. **权限结果**：允许的角色能做，越过 Team／店铺／动作范围的请求被实际执行端拒绝。
4. **平台证据**：外部写操作保留请求、执行结果和真实回读；异步接受不等于最终生效。
5. **异常证据**：至少覆盖正常、失败、重复触发／结果不明、部分成功及与本功能相关的边界情况。
6. **承接说明**：谁处理待确认、失败和平台不可用；试点尚未覆盖的流程由谁承接。

每条验收记录应写明版本、环境、Team／Store 范围、样本对象、操作人、预期与实际、证据位置、结论和未解决问题。文档中的业务样本使用虚构数据；实际验收材料不公开客户地址、凭证或访问令牌。

平台实测应在授权测试范围内进行。本次文档工作不执行真实上架、退款、发货或 Delete。

## 2. 各批次的交付门槛

| 批次 | 需要提供的成果 | 可以进入下一步的条件 |
|---|---|---|
| M0 地基 | Team／用户／权限、店铺连接、统一动作与任务、审计与保留边界的可运行验证 | A01–A06 全部通过；开发说明稳定身份、可空关系及历史如何承载，不要求业务方重新设计表 |
| M1 商品与 Listing | F03–F16 对应入口、平台能力核实记录、单条／批量结果、风险自动 Delete 证据 | A07–A19 全部通过；当前 Team 上线前风险专项通过；明确 M2 未就绪时的外部履约承接 |
| M2 履约与售后 | F17–F22 对应入口、采购数量与历史、发货和退款核实、物流可观察范围 | A20–A27 全部通过；采购、销售、物流、售后彼此不伪造状态；异常有负责人 |
| M3 完整 V1 | F23–F26、所有 P0 联调、账期与利润解释、运行与交接记录 | A28–A35 及此前场景通过；完成样本端到端核对；无未解决的发布阻断问题 |

平台实际不支持、账号不具备资格与 ERP 尚未实现必须分别记录。前两类可以形成有证据的能力限制，不能用“平台限制”掩盖后者；若影响当前 Team 核心闭环，必须限制试点或调整并明确确认发布范围，不能直接记为验收通过。

## 4. 发布阻断条件

出现以下任一问题，相关功能不能按完成交付；影响核心交易闭环时阻断对应批次生产开放：

- 跨 Team／店铺越权，或 Group／负责人隐式获得不应有的权限。
- 密钥暴露，或系统同步身份能无授权执行主动交易动作。
- 平台请求失败／未知却显示成功，或超时重试产生重复退款、发货等副作用。
- 普通 Delete／解绑／停用／日志清理导致交易、证据或历史责任丢失。
- 采购覆盖、发货、退款数量混淆，导致超量、重复或未覆盖需求被隐藏。
- 当前 Team 风险自动 Delete 未交付却开放其无人值守在线经营，或把策略默认应用给其他 Team。
- 未验证的 Walmart US 多包裹写入、平台不允许的 WFS 写操作被开放。
- 利润／回款计算重复扣费、重复累计或直接改写平台财务事实。

界面细节问题可以排入 P1，但不能用它给上述问题降级。平台暂不可用可以如实记录限制、待处理和外部承接，不能填写“平台验收通过”。

## 5. 分工与尚未承诺的内容

| 责任 | 应交付内容 |
|---|---|
| 产品／业务负责人 | 确认 Scope 分期和 Q01–Q06；提供真实团队规则、试点范围与责任人 |
| 开发团队 | 保持既有业务关系，完成 schema／实现；核实平台能力；解决防重复、异步与重试；提交可复核结果 |
| 测试／验收负责人 | 按场景验证正常与异常；记录版本、环境、样本、证据、缺陷和结论 |
| 运营／采购／财务 | 用实际工作样本核对数量、历史、平台结果、费用和异常承接 |

本文不规定表名、字段、接口路由、组件代码、重试次数、队列产品或开发工期，也不把已完成文档等同于系统已经实现。正式排期须在开发评估依赖与工作量后确认。
